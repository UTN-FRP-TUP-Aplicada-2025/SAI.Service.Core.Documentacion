
# El hallazgo duro: "retomar desde otro dispositivo" no es alcanzable

La SPEC pide (P-7, requisito crítico):

"La sesión debe poder retomarse desde otro dispositivo o después de un reinicio, con el progreso parcial intacto."

Por ADR-25, SAI.Service.Core corre en un contenedor en el propio host que el ejercicio apaga. Durante el apagón no hay UI en ningún dispositivo — la app está caída junto con el host, y --network host en localhost:8080 lo confirma. La mitad del requisito es satisfacible y la otra no:

Requisito	Verdicto
Retomar después de un reinicio, con progreso intacto	✅ Alcanzable (sesión persistida)
Retomar desde otro dispositivo durante el apagón	❌ No alcanzable con la arquitectura actual
Retomar desde otro dispositivo una vez que el host volvió	✅ Alcanzable (cualquier navegador abre el panel)
Esto no es un detalle: define el diseño. El ejercicio tiene una ventana ciega, y el asistente debe estar construido alrededor de eso, no pelearlo.

Consecuencia: el ejercicio son dos fases, no cuatro pasos
Físicamente es un solo apagón continuo que cubre los pasos 2, 3 y 4. La app muere una vez y vuelve una vez:

Paso	¿App viva?	Cómo se confirma
1 · Señal en batería	✅ Sí (el SAI la alimenta)	Automática, leyendo ups.status = OB
2 · Apagado ordenado	☠️ Muere durante	Se dispara antes; se confirma al volver (tiempo a mano, CU-10)
3 · Corte con retorno	☠️ Sin energía	Se dispara antes; se confirma al volver
4 · Arranque automático	🔄 Vuelve acá	Observación del operador al volver
Fase A (antes del apagón): confirmar paso 1 en vivo, y antes de disparar la secuencia mostrar un resumen de qué observar (el operador se queda sin pantalla; conviene que sea imprimible o anotable).
Fase B (al volver): el servicio arranca, detecta la sesión en curso y pide confirmar 2, 3 y 4 con lo observado.
Ojo con un matiz: que el servicio vuelva prueba que el host arrancó, pero no que arrancó solo — pudo prenderlo el operador. Así que el paso 4 sigue necesitando confirmación humana ("¿arrancó solo o lo prendiste vos?"), igual que hoy.

Modelo de dominio
Sigue el patrón que ya usa el proyecto (estado actual + hechos append-only, ADR-04 vía IEntidadHistoria):

SesionEjercicio — entidad de estado actual (como Verificacion): Codigo, IniciadaEn, FinalizadaEn?, Estado (EnCurso / Completada / Abandonada), FaseActual.
PasoEjercicio — hecho append-only (IEntidadHistoria): SesionCodigo, Supuesto, Resultado (Confirmado/Refutado/Omitido), ConfirmadoEn, Evidencia, MedicionSegundos?. Cada paso se persiste al confirmarse, nunca al final — que es justo lo que exige la SPEC.
Al confirmar cada paso, el asistente reusa los servicios que ya existen (VerificarSenalBateriaAsync, VerificarPresupuestoAsync, VerificarCorteConRetornoAsync, RegistrarReencendidoAsync): el asistente orquesta, no duplica la lógica de verificación.

Riesgos
Sesión zombi: si el host nunca vuelve, la sesión queda EnCurso para siempre. Necesita una salida explícita ("abandonar ejercicio") y quizá caducidad.
Doble camino: convivirán el asistente y la verificación individual (para renovar una prueba vencida suelta). Hay que evitar que se pisen — la sesión debería bloquear las acciones sueltas mientras esté en curso.
El paso 4 no es auto-confirmable (arriba). No hay forma de distinguir por software "arrancó solo" de "lo prendieron".
